# Questão 02 — Entrada Standard de Caracteres vs. Bibliotecas Legadas

## Pergunta

Historicamente, literaturas de C utilizam funções *unbuffered* de entrada definidas na biblioteca legada e não-padrão `<conio.h>`, tais como `getch()` e `getche()`, para ler caracteres imediatamente sem exigir que o usuário pressione [ENTER]. Sob a perspectiva da portabilidade moderna da linguagem e do padrão ANSI C:

a) Por que o uso de funções contidas em `<conio.h>` deve ser evitado em sistemas modernos (Linux, macOS, servidores)?

b) Quais são as funções equivalentes e portáveis fornecidas pela biblioteca padrão `<stdio.h>` para entrada e saída de caracteres?

c) Escreva um pequeno trecho de código padrão C que leia um caractere do console de maneira robusta, ignorando eventuais quebras de linha (`'\n'`) residuais no buffer do teclado.

---

## Resposta

### a)

O motivo principal é simples: **`<conio.h>` nunca fez parte do padrão da linguagem C**. Ela foi uma criação da Borland para os compiladores Turbo C e Borland C, que rodavam em MS-DOS.

Isso traz alguns problemas na prática:

- **Não compila em Linux nem macOS.** O GCC e o Clang nesses sistemas não têm esse arquivo. O programa simplesmente falha com `fatal error: conio.h: No such file or directory`.
- **Mesmo no Windows o comportamento varia.** Cada compilador implementa `getch()` de um jeito ligeiramente diferente, principalmente no tratamento de teclas especiais.
- **Assume um console de texto acessando o hardware diretamente**, modelo que não existe mais em terminais modernos, containers, servidores ou quando a entrada vem de um arquivo redirecionado.

O mesmo raciocínio vale para o `system("PAUSE")` que aparece na Questão 01: é um comando do `cmd.exe` do Windows e não funciona fora dele.

### b)

| Função de `<conio.h>` | Equivalente em `<stdio.h>` |
|---|---|
| `getch()` | `getchar()` |
| `getche()` | `getchar()` |
| `putch()` | `putchar()` |
| `cprintf()` | `printf()` |
| `cscanf()` | `scanf()` |

Também existem `fgetc(stdin)` e `fputc(c, stdout)`, versões mais genéricas que funcionam com qualquer fluxo de entrada/saída, e `fgets()` para ler uma linha inteira com segurança.

Uma diferença precisa ser dita: as funções de `<stdio.h>` esperam o `[ENTER]` para liberar os caracteres (são bufferizadas por linha). Não existe no C padrão uma forma portável de ler uma tecla imediatamente — para isso seria necessário recorrer a APIs do próprio sistema operacional. Para fins de portabilidade, aceita-se trabalhar com o modelo bufferizado.

### c)

O problema clássico acontece assim: depois de um `scanf("%d", &n)`, o `[ENTER]` que o usuário pressionou deixa um `'\n'` sobrando no buffer. A próxima leitura de caractere pega esse `'\n'` em vez de esperar o usuário digitar algo novo.

A solução é descartar esses caracteres antes de aceitar a entrada:

```c
#include <stdio.h>

int main(void) {
    int ch;
    int limpar;

    printf("Digite um caractere: ");

    // Descarta quebras de linha e espacos que sobraram no buffer
    do {
        ch = getchar();
    } while (ch == '\n' || ch == '\r' || ch == ' ' || ch == '\t');

    if (ch == EOF) {
        printf("\nEntrada encerrada.\n");
        return 1;
    }

    printf("Caractere lido: '%c' (ASCII %d)\n", ch, ch);

    // Limpa o resto da linha para nao atrapalhar leituras futuras
    while ((limpar = getchar()) != '\n' && limpar != EOF) {
        // descarta
    }

    return 0;
}
```

Um detalhe que costuma passar batido: a variável é declarada como `int`, não como `char`. Isso porque `getchar()` precisa conseguir devolver qualquer caractere **e também** o valor `EOF` (geralmente `-1`), que sinaliza fim de entrada. Um `char` pode não dar conta dessa faixa de valores, fazendo a comparação com `EOF` falhar.
